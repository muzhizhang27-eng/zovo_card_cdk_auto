## 已修复的行为

| 原始问题 | 修复后的行为 |
| --- | --- |
| 单码提交断网、页面停在确认页且不查单 | POST 前保存固定请求编号和提交标记，进入结果页；响应丢失、超时、502 等不明结果自动查单；刷新只恢复查询，不创建新请求 |
| 处理中从新链接切到另一张码，可能混用状态 | 未确认结果时保留原码、原令牌和原请求编号，继续查询原订单 |
| 批量网络异常直接判失败 | 已开始兑换的请求转入处理中并继续查单；兑换之前的预检网络错误允许重新输入凭证 |
| 批次进度仅在内存中 | 使用 sessionStorage 保存码序列、账号对应、令牌、请求编号、提交标记和状态；刷新恢复原队列并续查已提交订单 |
| 导入账号密码可能随完整状态一起保存 | 批次快照只保存恢复所需元数据，不序列化导入的 Session、Access Token、邮箱密码或 GPT 密码；未提交项在刷新后需重新粘贴或导入凭据 |
| 刷新或存储写入失败时容易丢失提交身份 | 写入浏览器存储成功后才允许发送兑换请求；存储不可用时停止提交并提示 |
| 批量请求容易触发限流 | Go 后端同一进程、同一上游的所有客户端共享配额：preview/preflight 间隔至少 2.1 秒、redeem 3.1 秒、result 1.1 秒；各 token 不单独获得新配额 |
| 收到 429 不等待重试 | 后端尊重 Retry-After 的秒数或 HTTP 日期，缺失时按 2/4 秒退避，最多额外重试 2 次；始终保持原请求体、请求编号和设备头 |
| 暂时限流被当作无效码 | 重试耗尽后，批量预览保留为待校验，可继续校验；不会把 429 当成卡密无效 |
| 结果轮询请求重叠、批量查询同时大量发出 | 单码查询完成后再安排下次查询；批量采用最多 6 条的轮转查询并共享后端配额 |
| 大批次等待输入凭证时预览令牌过期 | 提交前检查预览有效期，临近过期的未提交码重新预览后再预检 |
| 分域部署的设备头被 CORS 拦截 | 加入 X-Redemption-Device 允许头，保留来源白名单限制 |

仅明确收到 429 才在服务端自动重发。网络错误或 5xx 不自动重发兑换 POST；取消宽限期订阅的接口也不自动重试。HTTP 成功受理、running 和 review 均不作为最终开通成功，持续查询订单终态。

批次恢复覆盖同一浏览器标签页的刷新和站内切换。关闭标签页后的恢复取决于浏览器会话恢复行为；本次没有改成跨设备或永久保存凭据的方案。多进程或多服务器共用同一出口时，需要另设共享限流；当前限流在单个 Go 进程内共享。
